# Deliverance — Deploy to Render + Neon

Go-live guide. Nothing here happens automatically — you run each step. It puts Deliverance on Render
(Docker) backed by a Neon **production** database. Local dev is unaffected.

Ruby 3.3.6 · Rails 8.1.3 · production `./Dockerfile` (Thruster on port 80) · in-process Action Cable.

---

## What Phase 8 changed (already in your project)
- **`Dockerfile.dev`** + `compose.yaml` now builds from it — so `docker compose build` can never accidentally
  build the production image. The production **`./Dockerfile`** (generated by Rails) is what Render uses.
- **`config/cable.yml`** production → `async` (in-process), so live notifications/chat work on a single
  Render instance with **no Redis add-on**. (Multi-instance later → switch to redis + `REDIS_URL`.)
- **`.dockerignore`** now excludes `/setup/` so your dev secrets (`setup/env.filled`) never enter the image.
- **`render.yaml`** — a Render Blueprint for the web service.

## 0. Re-verify locally first (the dev build source changed)
```powershell
docker compose build
docker compose run --rm web bundle exec rspec
docker compose up
```
Expect the suite green and the app at http://localhost:3002 as before. Then `Ctrl+C`.

## 1. Create the Neon production database
1. In your Neon project → **Databases** → create a new database, e.g. `deliverance_production`.
2. **Connection string** → choose the **DIRECT / non-pooled** endpoint (the host **without** `-pooler`),
   with `?sslmode=require`. This is what runs migrations. Keep it handy — it's your `NEON_DATABASE_URL`.

## 2. Get your master key
Open `config/master.key` in the project (one line). That value becomes `RAILS_MASTER_KEY` on Render.
(It's git-ignored, so it won't be in your repo — you paste it into Render instead.)

## 3. Push the project to GitHub
```powershell
git add -A
git commit -m "Deliverance through Phase 8"
git branch -M main
git remote add origin https://github.com/<you>/deliverance.git   # your repo
git push -u origin main
```
(Confirm `.gitignore` lists `.env` — it does — so no secrets are pushed.)

## 4. Deploy on Render
**Option A — Blueprint (uses `render.yaml`):**
1. Render → **New → Blueprint** → connect the GitHub repo. It reads `render.yaml` and proposes the
   `deliverance` web service (Docker, `./Dockerfile`, health check `/up`).
2. Before the first deploy, set the two secret env vars:
   - `NEON_DATABASE_URL` = the direct Neon string from step 1
   - `RAILS_MASTER_KEY` = the value from `config/master.key`
3. Create — it builds the production image and deploys.

**Option B — Manual web service:**
1. Render → **New → Web Service** → connect the repo → **Language: Docker**.
2. **Dockerfile Path:** `./Dockerfile` (the production one — important).
3. **Environment variables:** `RAILS_ENV=production`, `NEON_DATABASE_URL=<direct Neon string>`,
   `RAILS_MASTER_KEY=<from config/master.key>`.
4. **Health check path:** `/up`. **Port:** the image exposes **80** (Thruster) — Render detects it; if it
   asks, set the port to `80`.
5. Create.

## 5. First boot migrates the database
The container entrypoint runs `db:prepare` when it starts the server, so the **first deploy loads the schema
into your Neon production database** automatically. Seeds are guarded to development, so **production starts
empty** (no demo data) — which is what you want for a real site.

## 6. Verify
Open the Render URL. You should get the Deliverance landing page over HTTPS. Register a Job Poster through the
modal, create a posting, register an Applicant, and click through apply → interview → messaging.

## Notes & gotchas
- **Empty on first launch.** Register real accounts on the live site to demo it. (If you later want the sample
  data in production, that's a small follow-up — we'd add a guarded one-off task rather than loosen the dev seed.)
- **Free plan** spins the service down when idle; the first request after that is a slow cold start. Normal.
- **Secrets** live only in Render's env vars and your local `.env` / `config/master.key` — never in the repo
  or the image. These dev keys should be **rotated** before any real use.
- **Region:** `render.yaml` uses `singapore` to sit near your `ap-southeast-1` Neon endpoint. Change if you like.
- **Live features** (bell, chat) use the in-process cable adapter — correct for one instance. If you scale to
  multiple instances, set `config/cable.yml` production back to `redis` and add a `REDIS_URL`.
- If a deploy hangs on "no open ports", confirm the **Dockerfile Path is `./Dockerfile`** (the production file)
  and the service port is **80** — the two things that bite Render + Rails 8 Docker deploys.
